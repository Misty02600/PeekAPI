# PLAN-0018：让录音 API 反映设备不健康状态

## 状态

讨论中

## 最后更新

2026-08-02

## 背景与目标

定义并实现 `/record` 的健康语义，使客户端能区分服务刚启动、暂时没有样本、设备重连中、录音已经停止
和设备长期不可用，而不是把所有空缓冲都解释成成功采集。

当前空缓冲会编码成有效空 WAV 并返回 HTTP 200，即使录音器的 `is_healthy` 为 false。现有 500 分支主要
表达 WAV 序列化失败，客户端因而可能把设备故障误判为正常但安静的音频。

## 已确认的事实和约束

- `AudioRecorder` 暴露 `is_recording` 与 `is_healthy` 两个布尔值，但读取它们没有形成对外一致快照，也没有
  区分 starting、reconnecting、stopping 等过渡状态。
- `get_audio()` 在缓冲为空时主动生成合法的单声道 PCM_16 空 WAV；`record_route()` 只在返回 `None` 时
  产生 500。
- 空缓冲既可能表示服务刚启动，也可能表示真实静音、重启后尚未采样或设备长期失败，不能只凭样本数判断
  设备健康。
- `/check` 当前是只返回 `ok` 的进程级健康检查，nonebot 客户端也把它用于主机可达性判断；直接改变它会
  扩大兼容影响。
- 计划必须与 PLAN-0017 的生命周期状态建模对齐，避免另建一套互相矛盾的健康状态。

## 技术路线草案

1. 先由 PLAN-0017 确定录音生命周期和线程安全快照，在一个锁保护的读取接口中返回当前状态、健康标记、
   缓冲样本数和必要的最近错误/更新时间，而不是让路由分别读取多个字段。
2. 为客户端设计稳定的状态枚举，例如 starting、healthy、reconnecting、stopped；只暴露客户端需要区分的
   粗粒度语义，不泄露线程实现细节。
3. 优先保持 `/record` 的 WAV 正文兼容，把健康状态放在独立 JSON 状态端点或可选响应头；如果最终选择在
   长期故障时返回 503，必须明确启动窗口、重试建议和旧客户端影响。
4. 路由只消费录音器的原子快照，文档同时说明“健康但暂时无样本”与“设备不可用”的差别。
5. 为状态转换、HTTP 映射和兼容路径补充单元/路由测试，再由 Windows 实机验证设备断开与恢复。

## 取舍与待决问题

- 使用独立 `/record/status`、扩展 `/check`、可选响应头，还是直接改变 `/record` 状态码。
- 启动后允许多长时间的无样本窗口；真实静音但设备健康时是否仍返回正常 WAV。
- 是否暴露最近错误和时间戳；这些字段有诊断价值，但会扩大长期 API 契约。
- 状态由录音线程主动维护，还是由线程状态、健康标记和缓冲快照按需推导。

## 希望最后是什么样

- API 文档能明确区分启动中、健康、重连中、停止和不可用。
- 客户端可以稳定识别设备故障，同时仍能取得现有 WAV 数据。
- 启动期和真实静音不会被误报为设备故障。
- 录音生命周期和对外健康语义由同一状态来源驱动。

## 做到什么算完成

- 先完成或对齐 PLAN-0017 的状态模型。
- 用户确认 HTTP 兼容策略和公开字段。
- 测试覆盖启动期、健康空缓冲、正常有样本、设备断开、重连和停止。
- nonebot 等已知客户端路径完成兼容检查。
- README、OpenAPI 描述与 audio recording flow 同步，并在成功提交后移入 `done/`。

## 涉及范围

- `src/peekapi/record.py`、`server.py`
- `tests/unit/test_record.py`、`tests/unit/test_server.py` 与真实录音集成测试
- README、OpenAPI 描述和 audio recording flow

## 怎么验证

使用可控假录音器驱动每个状态，验证对外状态码、响应头或 JSON 与 WAV 正文；再在 Windows 上断开/禁用
默认音频设备，确认客户端观察到重连或不可用，并在设备恢复后回到健康状态。最后执行 `just test`、
`just lint` 和 `just check`。
